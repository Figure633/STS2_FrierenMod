# 实施与验收计划

版本：v0.1；日期：2026-10-17。实施负责人按依赖推进，阶段完成以证据为准。当前只完成 G-1 文档与静态审计；以下开发、实机测试均尚未开始。不以日历承诺替代尚未验证的技术条件。

## 2. G0 必须回答的技术问题

| 实验 | 做法与通过条件 | 失败后的处理 |
|---|---|---|
| SPIKE-01 角色注册 | 目标版本加载最小角色，选择后进入战斗；记录实际模型/池注册方式 | 修正模板适配，不批量生成卡类 |
| SPIKE-02 自定义选择 | 展示三个候选、禁用一个、选择一次，返回战斗；关闭/场景切换不会卡死 | 优先用已验证的原生选择框，再评估自定义 UI |
| SPIKE-03 持久化 | 保存三槽和一张带参数生成牌，重启后恢复一致；明确游戏保存边界 | 查明支持接口，不写未验证的旁路存档 |
| SPIKE-04 资源 | 角色图、卡图、中文、音效打入PCK并被游戏加载 | 分离导出/路径/导入错误，不以DLL成功掩盖 |
| SPIKE-05 实例隔离 | 两个模拟玩家状态不串数据；确认多人入口和玩法模组限制机制 | 发布单人范围明确提示；多人不宣称兼容 |
| SPIKE-06 高风险可行性 | 调研生成牌保存、战斗快照、事件/首领接入；记录可用接口及限制 | 活动内容保留在范围台账，给出等价适配设计 |

## 3. 任务拆分与依赖

1. 建立真实工具链和版本记录，输出角色、卡牌、选择、存档的小样验证。
2. 建立稳定 ID 和内容注册/过滤，防止尚未实现内容进入奖励池。
3. 实现纯规则层：槽位约束、魔力费用、咏唱计划、同调和传说条件。
4. 接入游戏命令、事件生命周期和选择 UI，补事务取消、失效与重入处理。
5. 完成初始牌组、初始遗物和开局三槽；打通战后因子奖励、收藏和恢复。
6. 按“基础牌 → 咏唱/魔力经济 → 同调 → 传说爆发”补 Alpha 子集。
7. 实现菲伦专注/奇袭/融合/法杖，再迁移依赖这些机制的牌和双色牌。
8. 单独完成时间观念、自定义魔导书、特殊敌人等高风险模块，避免挤入普通卡批次。
9. 资源、语言、成就外观与发布兼容测试收口；对一代清单逐项解释差异。

## 4. 验收场景

以下均为计划用例，不是已通过结果。Unit 为规则测试；Integration 为游戏集成；Manual 为实机操作。

| 编号 | 层级 / 需求 | 前提与操作 | 预期 |
|---|---|---|---|
| T01 | Integration FR-001 | 启动、选择芙莉莲 | 10张正确起手、HolyEmblem；基线数值或已记录的目标适配一致 |
| T02 | Integration FR-001 | 选择菲伦 | 10张正确起手、HairAccessory及法杖面板；不出现芙莉莲开局三槽流程 |
| T03 | Integration FR-002 | 开局依次完成三次选择，安全边界保存恢复 | 已选槽/收藏不重复，候选不重抽，首战前槽位合法 |
| T04 | Unit FR-003 | 抽/手/弃/耗各有2张魔力 | 通用可用总数为6，每槽分别显示2；牌堆外预览不计数 |
| T05 | Unit FR-004 | X=2，倍率2，偏移1，专注1，弱化0 | requiredMana=4；对应堆3张时禁止，4张时支付4张，其他堆不变 |
| T06 | Unit FR-004 | T05状态加免费咏唱，目标堆0张 | 普通咏唱候选合法且支付0；预览不消费免费次数 |
| T07 | Integration FR-004 | 确认同一选择两次或重复投递操作ID | 只支付、激活、计数一次，UI正常返回 |
| T08 | Unit FR-004 | 空槽、三蓝图循环、无合法候选 | 显式不可用原因，无异常与无限递归 |
| T09 | Unit FR-004 | 精准咏唱魔力不整除费用，含专注/免费效果 | X按同一计算器求取有限合法值，实际支付与预览一致 |
| T10 | Integration FR-004 | 终极咏唱激活多个合法槽 | 因子按固定顺序各一次，整次完成事件一次；消费次数型豁免符合契约 |

## 5. 测试矩阵与覆盖口径

- 所有普通战斗牌至少覆盖基础/升级、合法/非法目标、支付与关键机制交互；具有多个独立分支的内容覆盖每个分支。选项牌、因子和生成牌不能因不进普通牌池而免验收。
- 代表构筑至少覆盖芙莉莲咏唱资源、同调循环、传说爆发，菲伦专注奇袭、融合生成；每角色另有低资源、异常负面状态和手牌上限场景。
- Alpha 至少完成 20 场固定场景、1 次正常全流程通关和3类保存点恢复。1.0 在固定版本各角色至少完成5次完整胜利流程，并覆盖正常失败/放弃后重开；该数量只是最低烟测门槛，不代表统计平衡结论。
- 每次游戏或依赖升级至少重跑 T01/T03～T17/T22/T24/T28～T30，受改动影响的其他模块追加测试。
- 与其他模组的兼容只列出实际测试组合，不宣称任意模组兼容。输入设备和平台也按实测列表声明。

## 6. 缺陷与发布阻断

P0缺陷：崩溃、坏档、复制资源、死循环、无法继续游戏、错误影响他人或原版角色。必须修复才能出公开包。

P1缺陷：主要机制错误、重要内容无法获得、升级无效、核心UI无法操作、明确支持语言缺关键文本。相关版本发布前必须修复。

P2缺陷：不妨碍操作的轻微显示/音画问题。可在明确列出已知问题、无关键内容缺失的情况下发布预览版；不能因此跳过完整移植的资源验收。

## 7. 验收报告格式

每次阶段验收记录：日期、代码提交、游戏构建/分支、依赖/引擎版本、平台/输入设备、种子/角色/构筑、测试编号、操作步骤、预期与实际、日志或截图位置、缺陷链接、通过/失败/未执行。未执行不能写成通过。

1.0 发布前逐项核对：有效内容覆盖率100%；没有未经说明的活动内容删除；P0/P1缺陷为0；存档迁移、干净安装和资源加载通过；兼容矩阵、已知问题与署名齐全。多人不作为单人1.0完成的隐含前提，但支持范围必须在下载说明中清楚标注。
