# 芙莉莲模组二代移植需求文档

版本：v0.1；日期：2026-10-17；状态：开发基线。需求依据为 [一代基线审计](01-一代基线审计.md)。本文规定目标行为，不表示已经实现。

## 1. 产品目标

让一代玩家在《杀戮尖塔 2》中继续体验芙莉莲的魔力管理与三槽咏唱，以及菲伦的专注、奇袭与融合构筑。移植应保留主题、核心决策和内容辨识度，同时适配二代的战斗、奖励、角色、存档与界面系统。

成功标准是完成一局可持续游玩的双角色模组：能够选择角色、开始冒险、形成构筑、跨房间保存恢复、完成结算。仅能加载 DLL、展示卡图或进入一场战斗不算完成。

## 2. 范围决策

| 交付层级 | 包含内容 | 不可混淆的边界 |
|---|---|---|
| G0 技术样机 | 最小角色、示例牌、选择流程、自定义状态保存、PCK 导出验证 | 不是玩法 Alpha |
| Alpha：芙莉莲闭环 | 原始起手、三槽开局、魔力、咏唱、同调、传说魔法、20 种起步卡、6 种因子、基础因子奖励和保存 | 明确标注内容子集，不宣称完整移植 |
| Beta：双角色主体 | 芙莉莲/菲伦主卡池、双色与生成牌、全部活动因子/道具、适配后的遗物药水、事件与特殊敌人 | 仍需关闭全部高风险偏差和发布测试 |
| 1.0：单人完整移植 | 默认启用且可达的一代内容全部有实现或明确等价适配，六语言键覆盖、原有美术音频和槽位外观成就处理完成 | 活动功能若仍被静默移除，不能标记“完整移植” |
| 后续多人版本 | 双人到目标游戏支持的最大人数，同角色与混合角色、同步、恢复和自定义选择验证 | 未通过验证前只承诺单人；G0 验证能否明确限制不支持的模式 |

修塔尔克、全注释角色交换、显式忽略旧内容和仅存在于 TODO 的设想不纳入 1.0。新增原创卡牌、大规模重平衡、从 STS1 导入局内存档不纳入本次移植。

优先级：P0 是 Alpha 所需；P1 是单人 1.0 所需；P2 是后续增强。P1 不是可随意删除的功能。若某项因目标接口无法实现，只能记录适配方案或发布为范围明确的预览版。

## 3. 用户流程

1. 安装依赖及模组，启动时能看到版本和依赖错误说明。
2. 选择芙莉莲或菲伦，看到正确角色说明、初始牌组和遗物。
3. 芙莉莲在首战前完成三槽因子选择；菲伦进入其独立的专注/法杖玩法。
4. 战斗中读取魔力数量、可用槽位、奇袭条件和生成牌预览，再作出操作。
5. 战后获得普通奖励及符合规则的因子奖励；在规则允许时配置魔法物品。
6. 经事件、商店、休息点成长，退出并继续游戏后恢复一致状态。
7. 胜利、失败或放弃后正确清理战斗状态，进入下一局不会继承上一局临时数据。

## 4. 功能需求

### 4.1 初始数据

一代起始数值作为首轮移植基线。二代全局规则若接管金币、抽牌或能量，优先走目标角色扩展点，偏差写入记录，禁止通过不受控全局补丁强行覆盖。

| 角色 | 生命 | 金币 | 每回合能量 / 抽牌 | 初始牌组 | 初始遗物 |
|---|---:|---:|---|---|---|
| 芙莉莲 | 75 | 99 | 3 / 5 | 打击×4、防御×3、流转×1、防御魔法×1、高速咏唱×1 | HolyEmblem |
| 菲伦 | 75 | 99 | 3 / 5 | Strike_Fern×4、Defend_Fern×4、CriticalHit×1、LieInWait×1 | HairAccessory |

### 4.2 Alpha 的明确内容子集

20 种卡牌按以下类名纳入，普通奖励池仍需遵守每张牌原有稀有度和基础牌规则：

`Strike_Frieren`、`Defend_Frieren`、`Flow`、`DefensiveMagic`、`RapidChant`、`OrdinaryOffensiveMagic`、`FireSpell`、`ContinualChant`、`PreciseChant`、`BackFlow`、`HighDensityMana`、`ManaExpansion`、`RedAppleSpell`、`Imagination`、`PerfectDefensiveMagic`、`LightningMagic`、`HellFireSummoning`、`RestraintMagic`、`Recall`、`RingletForm`。

6 种因子：`AdvancedDefensiveMagic`、`BarrierMagic`、`BigFire`、`BuildUpBody`、`HighSpeedMovement`、`BePrepared`。源码中 AdvancedDefensiveMagic、BuildUpBody、BePrepared 为 COMMON，另外三者为 UNCOMMON；开局三选一从合法 COMMON 候选取样，不改变稀有度。加入标签过滤后仍须验证每槽候选数不少于3，若不足则补入合适的原 COMMON 因子并记录集合修订。

`Mana` 等生成牌、上述卡牌依赖的能力与动作、必须的状态提示不计入“20 种”，但必须一并实现。Alpha 不能让已启用卡生成尚未实现的牌或因子；候选池要按已实现集合闭合。

## 5. 非功能需求

| 编号 | 要求 | 验收目标 |
|---|---|---|
| NFR-001 | 稳定性 | 发布测试无崩溃、卡死、存档损坏、无法结束回合或重复奖励等阻断缺陷 |
| NFR-002 | 可重复性 | 同版本、种子、选择序列得到一致的规则结果；预览、音画不推进玩法随机数 |
| NFR-003 | 隔离性 | 角色/玩家实例隔离；无全局共享可变牌堆、因子、充能、战斗计数 |
| NFR-004 | 性能 | 在记录配置的基准机上，普通牌操作新增逻辑开销目标 P95 ≤ 5 ms；UI 无超过 100 ms 的模组主线程阻塞，不含首次资源导入和动画等待 |
| NFR-005 | 资源加载 | 图片/音频按需缓存；战斗与界面关闭后无持续增长的资源持有；以固定 20 场测试观察趋势 |
| NFR-006 | 可维护性 | 规则与 Godot UI 分离；每个补丁有目标版本、原因和影响范围；依赖固定版本 |
| NFR-007 | 可访问性 | 1280×720、1920×1080、2560×1440 与游戏支持的 UI 缩放下关键操作可见；颜色之外有槽位文字/图标 |
| NFR-008 | 可诊断性 | 记录游戏/模组/依赖版本、内容 ID、操作上下文；错误日志默认不包含用户路径和身份信息 |
| NFR-009 | 兼容性 | 仅承诺版本矩阵实际验证的组合；Windows 首发，其他平台在构建及实机检查后列入支持 |

性能数值是初始工程目标，尚无测量基线；G0/G1 首次基准测试后可调整，但需保留前后结果与原因。

## 6. 平衡与适配原则

首次实现沿用一代数值和升级收益；优先确认语义正确，再评估二代敌人、能量经济和奖励节奏下的平衡。每项调整记录旧行为、新行为、触发原因和测试结果；不能以“移植”为理由同时无记录地改动费用、伤害和获取频率。

不移植一代反盗版逻辑、无关成就解锁绕过、写死原版敌人/遗物名称的排除列表。若旧设计依赖某个被屏蔽原版内容，则复现具体冲突，针对二代实际交互修复，而非默认删除原版内容。

## 7. 完成定义

一项内容只有在“已核对来源 → 已形成规则 → 已实现 → 已验证 → 已记录适配偏差”全部完成后才能计为移植完成。完整单人版本还必须通过 [发布验收](05-实施与验收计划.md)，关闭所有阻断风险，附安装说明、兼容版本、已知问题、署名和资源来源清单。

需求变更由当前实施负责人维护文档及决策记录；日常技术选择按本规范执行，不因常规实现细节反复中断开发。涉及玩家玩法范围的实质缩减应显式说明，不能藏在技术实现中。
