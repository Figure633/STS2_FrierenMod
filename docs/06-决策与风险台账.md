## 3. 实施台账与状态规则

自动生成的 `inventory/content.json` 是只读事实快照，重新审计会覆盖；每项 `implementation_status=not_started` 仅描述本轮未实现二代内容。后续人工实施状态单独记录在 `docs/content-specs/` 或受版本控制的移植台账，不写进可再生源文件。

状态流：`待核对 → 已规格化 → 实现中 → 待验证 → 已验证`。另设 `历史排除` 和 `适配中`。不能用“写了类文件”直接标记已验证。

完整性口径：分母是固定一代基线中默认启用且实际可达的独立内容身份，含非普通卡池的生成、选项、因子和事件；抽象类、注释文件与被关闭内容不计。完成率必须分角色卡、因子道具、遗物药水、事件敌人等类别报告，不能以大量简单选项牌掩盖未完成核心机制。

## 4. 偏差记录模板

每个与一代不同的行为建立 `DEV-xxx`：

```text
标题：
关联需求 / 机制 / 测试编号：
旧来源：固定提交 + 文件 + 行号
一代观察：区分静态推断与游戏复现
二代限制或修正理由：
采用行为：包括时点、支付、范围、保存与UI
玩家影响：
替代方案及不采用理由：
实现提交与验证结果：
状态：拟定 / 已实现 / 已验证
```

首批需建立的偏差项：免费咏唱判定统一、精准/终极免费时X上限、终极咏唱事件次数、装载安全窗口、二代开局事件接入、原版独有内容映射、时间观念快照字段。

## 5. 后续所需外部信息

进入G0时需要实际游戏安装路径与分支、可用MegaDot版本、BaseLib版本；先从本机已有环境定位，无法找到时再集中询问。后续可选参考包括一代正式发布包或作者提供的代表性玩法录像，用于关闭静态源码与实玩表现之间的歧义。

素材授权/署名信息在具体素材接入时从既有记录与作者贡献清单补齐。本轮没有修改、发布或分发任何游戏内容，没有将未验证项宣称为可用成品。
