# 技术与开发规范

版本：v0.1；日期：2026-10-17。下文的模块名、服务名和数据字段是项目设计，不冒充二代原生 API。具体游戏类型和钩子必须由 G0 对目标版本编译与运行确认。

## 1. 技术路线与兼容基线

采用 C#、与目标游戏匹配的 Godot/MegaDot、BaseLib 角色/内容扩展；必要时以 Harmony 做最小范围补丁。Java 源码用作行为规格和资源索引，不能直接作为二代运行时依赖。

已检查的参考模板为 Alchyr/ModTemplate-StS2 提交 `2c900a04dd2073872f677f4fb78ee2ad1e871009`。其角色工程声明 `net9.0`、`Godot.NET.Sdk/4.5.1`，使用 `PlaceholderCharacterModel`、`CustomCardModel` 和 `ModInitializer`。这些符号只证明该模板的当前实现；本项目正式角色不能长期保留占位角色资源。

来源：[角色工程文件](https://github.com/Alchyr/ModTemplate-StS2/blob/2c900a04dd2073872f677f4fb78ee2ad1e871009/content/CharacterModTemplate/CharMod.csproj)、[角色示例](https://github.com/Alchyr/ModTemplate-StS2/blob/2c900a04dd2073872f677f4fb78ee2ad1e871009/content/CharacterModTemplate/CharModCode/Character/CharMod.cs)、[初始化入口](https://github.com/Alchyr/ModTemplate-StS2/blob/2c900a04dd2073872f677f4fb78ee2ad1e871009/content/CharacterModTemplate/CharModCode/MainFile.cs)。

G0 建立 `compatibility.json`，记录以下实测值；在此之前均为未锁定：

| 字段 | 要求 |
|---|---|
| gameVersion / gameBuildId / branch | 实际测试游戏版本与分支，不能填模板最低版本冒充 |
| gameAssemblyHash | 本地合法安装的目标程序集 SHA-256，仅记录哈希，不分发游戏 DLL |
| dotnetSdk / targetFramework | 实际编译组合，SDK 版本与目标框架分开记录 |
| engineVersion / exportTemplates | 实际 MegaDot/Godot 与导出模板版本 |
| baseLibVersion / analyzerVersion / harmonyVersion | 构建与运行所用确切版本 |
| templateCommit | 所用模板固定提交 |
| supportedPlatforms / verifiedModes | 实测平台与单人/多人状态 |
| verificationEvidence | 编译、启动、选择、保存和资源测试记录路径 |

禁止在发布工程中留下 NuGet `Version="*"`。保存依赖锁文件，兼容版本升级作为独立变更，至少重跑核心机制、加载、存档和界面冒烟。

## 2. 目录与模块边界

以下为规划目录；当前只创建文档与审计工具，未创建假工程或未验证 API 占位实现。

```text
STS2_FrierenMod/
  README.md
  docs/                     # 需求、机制、技术、验收、决策
    inventory/              # 可再生的一代审计结果
    content-specs/          # 逐项行为规格（实现对应批次时补齐）
    decisions/              # 适配偏差与技术决策
  src/
    FrierenMod/             # 唯一运行时入口、角色与内容注册、Godot资源项目
      Characters/
      Cards/ Relics/ Potions/ Powers/ Events/ Encounters/
      Domain/               # 无UI依赖的费用、槽位、判定、组合蓝图
      Integration/          # 游戏命令、生命周期、BaseLib、最小补丁
      Persistence/          # 版本化DTO与迁移
      Presentation/         # 三槽UI、法杖UI、资源表现
      Localization/
  assets-source/            # 已选用原始素材与来源表
  tests/                    # 核心规则测试与集成场景，随功能加入
  tools/                    # 审计、校验、构建、打包脚本
  dist/                     # 发布产物，不提交缓存或游戏文件
```

依赖方向：展示层读取规则快照并提交操作；集成层把操作转为游戏命令；规则层决定资格和参数；持久化层转换数据。规则层不读取鼠标、不操作 Node、不调用文件系统、不直接改变其他玩家。

普通卡牌不要求“全配置化”。能用清晰卡类表达的行为直接实现，重复的费用、槽位、事件和生成牌组合放入公共模块。避免用庞大解释器复制整个游戏引擎。

## 3. 一代到二代的映射

| 一代对象 | 二代项目责任 | 禁止直接移植的模式 |
|---|---|---|
| ModManager/BaseMod 注册 | 统一入口与明确内容池，框架注册行为在 G0 实测 | 假定所有类自动扫描或所有遗物归芙莉莲 |
| AbstractBaseCard/CardInfo | 二代卡模型、升级逻辑和动态变量 | Java 费用负数哨兵直接当二代费用 |
| AbstractGameAction 队列 | 目标游戏命令/异步结算适配层 | UI 中直接改血、牌堆、回合、掉落 |
| SpirePatch/SpireField | 首选正式扩展点，必要时封装最小 Harmony 补丁 | 一代字节码行号/局部变量补丁机械翻译 |
| MagicDeckField/Slot | 每玩家局内收藏及战斗装载状态 | 静态全局收藏或依赖当前 UI 玩家 |
| AbstractMagicItem | 因子/道具领域模型与 UI 展示映射 | 把所有魔法物品当普通奖励卡注册 |
| CardModifier | 有类型、有顺序、可保存的卡牌修饰描述 | 任意反射克隆和运行时对象图序列化 |
| 自定义屏幕与 SpriteBatch | Godot 场景、布局、输入与焦点 | 逐像素照搬旧分辨率坐标 |
| RandomField | 引擎种子体系中的明确玩法随机流 | `new Random()`、时间戳随机、渲染消耗 RNG |
| SaveFileHelper | 版本化状态存储与迁移 | 序列化 Java 类名、Node、反射字段或旧存档格式 |

## 4. ID、内容与规则编码

项目运行时 ModId 暂定 `FrierenMod`，命名空间 `FrierenMod`，产品名“葬送的芙莉莲”。注册前做冲突检查。稳定内容键采用显式常量，例如内部键 `card/frieren/rapid_chant`；转换为目标游戏 ModelId 的具体格式在 G0 验证，禁止自行假设冒号格式被原生识别。

维护 `legacyId → stableKey → runtimeModelId → localizationKey → resourcePath` 映射。旧 ID 只作追踪；不因此承诺 STS1 存档兼容。C# 重命名不能自动改变已发布存档 ID。共享/双色牌可共享规则实现，但所有权与池归属明确；如框架需要两个注册 ID，要保存对应关系并避免奖励权重翻倍。

卡牌费用、伤害、格挡、X、升级差值分别存储。预览只调用纯函数；随机和状态变化只发生在提交阶段。动态卡描述来自实际参数，不再维护与代码独立的手写最终数值。

规则事件至少区分 CardPlayed、FactorActivated、ChantCompleted、SynchroResolved、RaidTriggered、RaidCompleted、SpecializedMagicCreated。它们是项目内部事件语义，具体如何挂接游戏回调由集成层负责。事件包含 owner、source、operationId 和必要上下文，订阅生命周期必须可解除。

## 5. 存档与恢复

只承诺目标游戏允许保存的边界；不能先假定任意战斗中间可存档。G0 确认选择中断时的恢复机制：若游戏不支持中途保存，则将自定义选择设为完整事务，并只在可保存边界写入完成状态，不伪造支持。

| 数据层 | 应包含 | 不应包含 |
|---|---|---|
| Profile | 槽位外观解锁、教程标记、显示/声音设置 | 临时战斗强度与他人状态 |
| RunPlayer | 玩家稳定身份、因子/道具实例、槽位、掉落修正、法杖永久上限、组合牌蓝图 | Node 指针、UI坐标 |
| CombatPlayer | 临时槽变更、专注、融合、法杖当前充能、封印区、临时修饰、时间快照 | 未声明的引擎对象图 |
| Turn | 咏唱牌数、奇袭次数、回火修饰、已提交操作标识 | 跨战斗永久解锁 |
| Presentation | 面板开关、悬停、动画播放位置 | 任何决定胜负的唯一状态 |

保存包装包含 `schemaVersion`、`modVersion`、兼容信息、状态所属玩家和载荷。魔法物品保存稳定内容键、实例 ID 和槽位；生成牌保存基础模板、升级、参数和有序修饰列表；随机状态通过目标引擎受支持的保存方式保存，不自行重播猜测。

恢复顺序：校验版本与数据 → 迁移到当前 schema → 建立内容/实例映射 → 恢复收藏和生成牌 → 恢复槽位与计数 → 重建 UI。期间不发放奖励、不消耗 RNG、不重复触发获取遗物效果。

未知内容键、缺少必需字段、无可用迁移链时保留原始存档并报告兼容问题，不静默丢牌。可选纯外观键允许回退到默认。schema 单调递增；每次改变保存语义必须附旧版夹具恢复测试。1.0 后维持同一主版本的明确迁移路径，不承诺降级读取。

## 6. 随机数、多人和异步

随机流按用途区分初始因子、战后掉落、战斗随机目标、随机生成内容；使用游戏提供的确定性机制或经验证的扩展。候选池在抽取前按稳定内容 ID 排序，空池返回显式无奖励/无目标，不能调用随机索引越界。不得用当前时间、运行时哈希或遍历无序字典决定玩法。

多人规则从架构开始隔离，但支持状态以实测为准。操作携带玩家身份，远端 UI 不拥有修改权；同一操作只提交一次。不得自行建立与游戏并行的未经验证网络协议。G0 查明原生/框架的权威执行和选择同步方式；后续多人版本复用该方式。

异步动作必须可在战斗结束、目标死亡、玩家掉线或场景关闭时结束；避免 `.Wait()`/`.Result` 阻塞主线程。动画不决定规则是否成功，禁音和跳过动画不得改变结果。错误要回收交互锁与临时对象，不能留下永远等待的选择任务。

## 7. 补丁与兼容规范

优先级依次为已验证的游戏扩展点、BaseLib 扩展、局部 Harmony 补丁。每个补丁登记目标类型/方法签名、适用版本、目的、角色过滤、失败行为和冲突测试。运行版本不匹配时有明确诊断，不能让核心补丁部分失效后继续提供看似正常的内容。

旧 `AntiPirateHelper`、泛化修改成就的逻辑和全局移除原版遗物/首领的默认行为不迁移。旧代码若为规避具体冲突，先复现二代冲突再决定局部处理。原版敌人的“鸟类”等判定建立显式、可维护的目标映射，不能依赖名称包含某个汉字。

## 8. 美术、音频与本地化规范

资源来源顺序：已对齐基线的本地源码资源 → 对应 GitHub 资源 → 其他本地高清源。`assets-source` 保留选用原件，运行资源按目标格式导出；不改写 `STS1_素材`。每个选用资源登记来源路径、哈希、作者/署名、用途、加工步骤、目标路径和使用状态。未核对的资源不能标成已确认。

参考模板普通卡图建议大图 1000×760、小图 250×190，全幅卡图 606×852、小图 250×350；实际裁切要用游戏内预览验证，不能靠放大低分辨率伪装高清。来源：[卡牌资源示例](https://github.com/Alchyr/ModTemplate-StS2/blob/2c900a04dd2073872f677f4fb78ee2ad1e871009/content/CharacterModTemplate/CharModCode/Cards/CharModCard.cs)。

Spine atlas/JSON、动画、字体和音频分别进行兼容实验；旧动画文件不能保证直接导入。临时静态立绘可用于内部样机，正式资源替换是发布验收项。音效/BGM 可分别关闭，循环、停止和场景退出行为必须明确。

本地化采用目标游戏格式，由转换器映射 ZHS/ZHT/ENG/JPN/KOR/RUS。旧 `!D!`、`NL`、颜色和关键词标记不能原样塞入二代字符串；每种语法建立转换及校验。Alpha 保证简中和英文回退可用；1.0 所有支持语言的有效键齐全并完成抽样人工校对，缺失项以明确回退显示，不宣称机翻即人工验收。

## 9. 工程、质量与发布

- C# 开启可空引用检查；约定类/公开成员 PascalCase、局部变量 camelCase；禁止以吞异常维持表面正常。
- 一个变更围绕一个机制或一批关联内容；需求、代码、资源、语言与验收记录保持对应。生成清单不手改，通过审计脚本刷新；人工移植状态放独立台账。
- 测试重点是规则边界、存档和异步事务，不为简单常量或可逆文档变化堆砌镜像测试。
- 构建、安装、发布分开。参考模板会自动复制到 mods 且 PCK 导出可继续报 warning；本项目改为默认只写工作区 `dist/`，显式部署命令才写游戏目录，PCK 导出失败必须使发布失败。
- 干净构建必须验证 DLL、PCK、manifest 三件套、资源实际可加载、版本一致和哈希。构建成功不等于游戏加载成功。
- 不将 `sts2.dll`、游戏原始资源、用户存档、绝对机器路径和构建缓存打入发布包。保留第三方许可证与作者署名。
- 发布包附 README、安装步骤、依赖版本、兼容矩阵、变更记录、已知问题和资源署名；升级先备份模组存档，不自动覆盖未知版本数据。

计划的检查顺序为：内容/本地化/资源静态校验 → 编译与规则测试 → 导出 → 实机加载 → 代表性战斗与保存恢复 → 干净安装。当前尚未建立这些运行时脚本，也未执行游戏测试。
